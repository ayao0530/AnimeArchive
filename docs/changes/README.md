# 变更记录（Change Log）

> 本目录存放**实施阶段之后**的所有改动：实测反馈的 bug 修复、实现期新增决策、以及过程中踩到的坑。
>
> **为什么不写进 `需求与设计文档.md`**：那份文档是**需求与设计的基线**，越写越厚会「打开困难、也不好看」，
> 而且需求与后来的改动混在一起，翻起来分不清哪条是当前有效的。

---

## 1. 归档规则（约定）

| 规则 | 说明 |
| --- | --- |
| **按日期分文件** | 一个会话 / 一批改动一个文件：`YYYY-MM-DD.md`（如 `2026-09-13.md`） |
| **文件内按主题分小节** | 例如「归档正确性」「文件与目录安全」「媒体库交互」「性能」 |
| **条目编号** | `YYYY-MM-DD #n`（同日递增）。跨文件引用就写全，如 `2026-09-12 #5` |
| **每条四段** | **现象 → 原因 → 做法 → 验证**（验证必须写可执行的东西：自检编号 / 实测数字 / 命令） |
| **冲突以更新的为准** | 若本条与更早的记录或 `需求与设计文档.md` 正文冲突，**以日期更新者为准**；<br>并且**必须在被取代的那一条上显式标注**：`⚠️ 已被 2026-09-13 #2 取代` |
| **不要就地改写历史** | 老的记录保留原样（只加取代标注），方便回溯「当时为什么这么做」 |
| **文档分工** | 需求/设计基线 → `需求与设计文档.md`；本目录 → 改动与决策；<br>`实施提示词.md` §10 → 坑清单（索引式速查）；<br>`docs/使用与运维.md` → 使用 / 运维 / 代码级细节（第 5 章）；`README.md`（仓库根）→ 对外介绍 |

---

## 2. 效力顺序（冲突时照这个来）

```
docs/changes/<更晚日期>.md   ←  最高（最新事实）
        ↓
docs/changes/<更早日期>.md
        ↓
docs/需求与设计文档.md        ←  基线；正文里的旧描述若与本目录冲突，以本目录为准
        ↓
docs/实施提示词.md            ←  开工前写的预判（§10.1 里明确标注了错的条目）
```

> ⚠️ 一句话：**越新越算**。但「新」不代表老的是错的 —— 很多决策只是被更具体的场景细化了，
> 所以每条都写清楚「现象/原因」，别只留结论。

## 4. 新增一条时怎么做

1. 找到（或新建）今天的 `YYYY-MM-DD.md`；
2. 在对应主题小节里按四段式追加一条，编号取当日递增；
3. 如果这条**推翻了**旧的决策/描述 → 去旧的那条上加 `⚠️ 已被 <新编号> 取代`，并在本文档第 3 节索引里补一句要点；
4. 如果新踩的坑对「以后开工」有普适价值 → 顺手在 `实施提示词.md` §10 补一行（只写一行 + 指向本目录）。
