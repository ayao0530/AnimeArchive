## 一、归档正确性

### #1 多季作品被归到别的季 —— 别名表脏数据（在线检索没有纠正机会）

- **现象**：`[ANi] 小書痴的下剋上 為了成為圖書管理員不擇手段！領主的養女 - 21`（第四季）
  被自动归到**第一季**文件夹 `小书痴的下克上 〜为了成为图书管理员而不择手段〜`（2019/10）。
  （用户 09-12 反馈；日志还原：15:39 那批还是对的 → **15:45 脏记录被写入** → 15:55 那一集归错。）
- **原因**：别名表里有 6 条旧写入的**脏记录**（第一季条目把第四季的名字当成了自己的别名），
  且 `src=manual`、置信度 **1.0** ⇒ `lookup()` 的 `direct` 原始键查询精确命中，L2/L3 **完全没有纠正的机会**。
  脏键里含 `擇` 而非 `择` ⇒ 是旧的不完整繁简表时期写进去的（见 `2026-09-12 #8`）。
- **做法（一读一写，缺一不可）**：
  1. **读时复核「更具体者胜」**（`normalizer.ts`）：L1 精确命中后再比一次，若存在一个名字
     ①更**长**（更具体）②**包含**当前名字 ③与文件名相似度 ≥ 0.8 ④比当前命中高出 ≥ 0.03，就采纳更具体的那个。
     两个证据源：别名表官方名 + **归档区里已存在的番剧文件夹**（用户已手工确认过的结果最可靠）。
  2. **写时护栏**（`store.upsertAlias`）：别名**更长且与官方名相似度 ≥ 0.8** 时判为「另一季的标题」**拒收**。
     ⚠️ 这里不能用「字面包含」：繁简与装饰符会让包含失效（`…不擇手段！領主的養女` vs `…〜而不择手段〜`）。
- **实测**：第四季文件对第一季名 **0.822** / 对第四季名 **0.915**（`S4键.includes(S1键)=true`）⇒ 选第四季；
  第一季文件反向 **0.909 / 0.823** ⇒ 不会被抢；已精确命中时相似度≈1.0 ⇒ 天然不可能被抢。
  ⚠️ 只比「谁更相似」不够：`Full Dive` 对 `CLANNAD` 也有 0.179（对正确名字却是 0.000），
  必须有「包含 + 绝对阈值」两道闸（这一点曾把 A5/A7/A8/A13 全部带崩）。
- **数据修复**：备份 `data/aliases.backup-<ts>.json` 后剔除脏别名、删脏键、给正确的第四季条目补键。
  ⚠️ **必须先停服再改文件**，否则服务内存里的旧表会在 `flush()` 时覆盖修复；
  ⚠️ 比对别名要用 `aliasKey(a) === aliasKey(x)`，别用 `===` 字面比较（别名里多一个空格就匹配不到）。
- **验证**：自检 **A37 / A38**；真实扫描日志 `ℹ 已载入 709 个已归档番剧文件夹`，目标路径正确。
- ⚠️ **性能教训**：第一版遍历 3600+ 条键、热循环里现场算键 = **229 ms/名字 ≈ 每次扫描多花 172 s**；
  改成按**官方名**去重（3619 → 721）+ 预计算键 + `WeakMap` 缓存文件夹键 = **0.62 ms/名字（约 1%）**。

## 二、媒体库：浏览与展示

### #2 四层折叠，且默认全部折叠

- **现象**：媒体库一进来全铺开 —— 一个年份上千个文件，滚动卡、也难找。
- **做法**：年份 / 月份 / 番剧卡片 / 子目录**四层都默认折叠**，折叠时**不渲染**子树；
  **检索时自动全部展开**；检索期间的点击记在「覆盖」里（优先级高于强制展开），**检索词一变就清空覆盖**
  （否则搜索期间用户点了没反应）。
  ⚠️ 折叠键要加 `lib-` 前缀 —— 归档视图用的是 `y2026`，两边共用 store 里同一张折叠表。
- **验证**（2026 年，Playwright 数 DOM）：初始只渲染 9 个年份行、**245 个 DOM 节点**；
  逐层展开到子目录才 940 个。点子目录行里的按钮**不会**把该行误折叠（`stopPropagation` 有效）。

### #3 文件行按「集数数字」排，不是按文件名字符串

- **现象**：同一部番剧混了两个字幕组（`[BeanSub&FZSD]…` / `[Nekomoe kissaten]…`），
  列表里 01 后面直接跟 14，02 要翻到另一段才出现。
- **原因**：索引（`readdir` 原顺序 = 名字序）与前端渲染都照数组顺序 ⇒ 两个字幕组各自排成一堆。
- **做法**：新增 `compareByEpisode`，**两处都改**（只改一处会不一致）：
  前端（渲染时排，**立即生效、不用重建索引**）+ 服务端索引（`indexer` 收集完 `sort`，下次重建/归档后生效）。
  规则：① 有集数的在前，按数值；② 同集数按后缀（`24` 在 `24v2` 前）；③ 解析不出集数的（NCOP/特典/未识别）**放最后**。
- **验证**：自检 **A39**；实测顶层 `01 02 03 04 06 … 23 24 24v2 25` 递增，
  子目录 `05 05 05 —` 递增。
  ⚠️ 验证时注意：顶层与子目录是**两个容器各自排序**，整串检查递增会误报。

## 三、媒体库：多选与批量移动

### #4 多选 + 批量移动

- **做法**：文件行勾选框 + 卡片头 / 子目录行**三态「全选」**（全选 / 部分 / 未选）；
  选择集**跨卡片、跨年份**累积（只存文件路径，不存对象 —— 搬完索引会重载）；
  底部固定条 + **卡片头就地入口**；批量走 `/api/library/move-batch`（**只重建一次索引**，逐条调单文件接口会每搬一条重建一次）。
  搬完自动清空勾选；失败则保留（可直接重试）。
- **验证**：勾 11 个后卡片头出现「↗ 移动选中的 11 个」，弹窗里**正好 11 条**；
  零副作用全链路验证手法＝**目标填成它现在的位置**（接口返回 `unchanged`，磁盘零改动）。

### #5 🔴 「移动」入口同名，导致整个文件夹被搬走

- **现象**：用户勾了 1 个文件、点了「批量移动」，结果**同一文件夹里 24 个文件全被搬走**。
- **原因**：番剧卡片头原本就有「↗ 批量移动」（语义＝移整部），新加的底部条按钮也叫「↗ 批量移动」（语义＝移勾选）。
  同名 + 就近可点 ⇒ 点错。日志（`batch-library-move.jsonl`）可完整还原误移并精确回滚。
- **做法**：**同一视图里多个「移动」入口，文案必须自带范围与数量**（并给就地入口加强调色）：

  | 位置 | 文案 | 作用范围 |
  | --- | --- | --- |
  | 番剧卡片头 | `↗ 整部移动（N）` | 这一部番剧的**全部**文件 |
  | 番剧卡片头（有勾选时才出现） | `↗ 移动选中的 N 个` | **只**这一部里勾选的那些 |
  | 子目录行 | `↗ 移动整个目录` | 那个子目录（含里面所有文件） |
  | 文件行 | `↗ 移动` | **只这一个**文件 |
  | 底部选择条 | `↗ 移动选中 N 个`（强调色） | 跨卡片的**全部**勾选项 |

  ⚠️ 排查这类「勾选没用」的反馈要**先量证据再改代码**：勾 1/24 个后点底部条看弹窗条目数
  （=1 说明选择逻辑没问题，问题在按钮歧义）。
- **误移回滚实操（可复用）**：从 `batch-library-move.jsonl` 精确取 `fromPath`(原)/`toPath`(现) 对
  → 校验每个 `toPath` 仍存在 → `POST /api/library/move-batch`（`fromPaths` + 原 `zhName/year/month`）一次性搬回。
  实测 24 个文件 / 10.32 GB 还原成功。
  ⚠️ 接口响应体是 `{ok,data:{…}}`，读 `$r.moved` 会全是空值，要读 **`$r.data.moved`**。

### #6 入口必须「就地」，只放底部条不够

- **现象**：用户勾选后问「怎么只移动我勾选的那几个」—— 底部浮条没被注意到（截图/视野里常常只有内容区）。
- **做法**：勾选后**卡片头就地多出** `↗ 移动选中的 N 个`（强调色，仅 `selCount>0` 时渲染）；
  列表顶部说明也写明用法；底部条保留作跨卡片汇总入口。
  ⚠️ 底部条用 `createPortal` 挂到 `document.body`（`.panel` 是 `overflow:hidden` 的滚动容器，不再依赖「fixed 不受祖先影响」）。

## 四、可靠性：反馈、进度、刷新

### #7 长耗时操作没有反馈 ⇒ 用户重复点击 ⇒ 重复操作

- **现象**：点「应用」后弹窗立刻关，然后默默搬几十秒（NAS 上几 GB）；用户以为没生效 → 再点一次。
- **做法**：**弹窗保持打开**并显示
  「⏳ 正在移动 12 个文件（3.9 GB）…（已用 N 秒，请勿重复点击）」，两个按钮 `disabled`；
  搬完显示「正在刷新媒体库…」再关闭。秒表贯穿整个操作（不分段重置）＝「还活着」的信号。
  单文件「↩ 撤回」/「✏️ 改名」也走全局忙碌遮罩，并在入口 `if (busy) return` 忽略重复点击。
- **验证**：用 `page.addInitScript` 包装 `fetch` 把批量移动拖慢 6 秒 —— 1.5s 时弹窗仍在、提示「已用 1 秒」、
  两个按钮禁用；4.5s 时「已用 4 秒」；结束自动关闭并清空勾选。
  ⚠️ Playwright 的 `page.route` 拦截在这个环境**不生效**（真实请求照发），要用包装 `fetch` 的办法；
  ⚠️ `addInitScript` 每次导航都会重跑 ⇒ 跨导航传状态要用 localStorage。

### #8 索引刷新失败只写日志 ⇒ 列表显示旧数据 ⇒ 用户以为没生效

- **做法**：`loadLibrary()` 失败**自动重试一次**；仍失败 `set({libraryError})` →
  列表顶部红色提示条「⚠ 索引刷新失败（服务可能正忙）」+「↻ 重试」按钮；成功后自动清除。
- **验证**：注入索引读取失败 → 红条出现且可见、有重试按钮；去掉注入后点「重试」→ 红条消失、9 个年份正常载入。

## 六、发布准备

### #10 发布到 GitHub 前，把文档与源码里的真实环境信息全部脱敏

- **现象**：准备把仓库推到 GitHub，但源码 / 文档 / 自检脚本里到处是**本机真实环境**：
  NAS 主机名与共享名、项目所在的盘符目录、Windows 用户名、以及「作者自己的媒体库清单」。
  直接推上去等于把家庭网络结构 + 个人观影记录公开。
- **风险点（逐一排查过）**：
  1. `README.md` 与各文档正文里的 `\\<NAS 主机名>\<共享名>\…`；
  2. 文档里 `<盘符>:\<项目目录>`、e2e 注释里的 `C:\Users\<用户名>\AppData\…`；
  3. **最容易漏的两处**：`server/data/`（11.5 MB：`config.json` 带真实归档根、`logs/` 每条都记完整
     文件路径、`aliases.json`、Bangumi 缓存）与 `web/data/` + `web/public/data/`（各 9.9 MB：
     索引里列着所有番剧名与文件名）；以及 `.tools/`（102 MB 便携 Node）；
  4. **自检命令本身**：原本想写的示例扫描命令里直接写了真实主机名 —— 这本身又是一次泄漏。
- **做法**：
  - **统一占位符**：`\\NAS\share\已看`（NAS）、`<项目目录>`（本地项目目录）、`<盘符>:\<挂载点>\…`、
    `<本地临时目录>`（用户名）；只在**事故复盘**里保留结构性描述（UNC 前缀被压成 `\<share>`），不再出现真实值。
  - **`.gitignore` 收紧**：`.tools/`、`node_modules/`、`dist/`、`server/data/`、`web/data/`、
    `web/public/data/`、`web/dist/`、别名备份、`*.tmp`、`.e2e/`、编辑器与本机 OS 垃圾文件。
  - **README 拆分**：把原根目录 `README.md`（使用/运维/构建/自检/工程细节，738 行、满是本机信息）整体
    迁到 `docs/使用与运维.md` 并脱敏；根目录**新写一份对外 `README.md`**（功能、快速开始、关键设计、
    目录结构、自检、文档索引、隐私说明、限制），正文不含任何真实路径。
  - **配图不用真机**：截图取自静态 Demo `demo/index.html`（模拟数据，路径一律 `\\NAS\Media`），
    存为 `docs/images/demo-archive.png` / `demo-library.png`；**绝不**截真实媒体库（会暴露番剧与文件名）。
  - 同步修正所有指向旧 README 的交叉引用（`docs/使用与运维.md` 第 5 章、§11 等）。
- **验证**：
  - 全仓扫描 65 个「会被提交的文件」，检查项＝真实 NAS 主机名 / 真实共享名 / 本机盘符与项目目录 /
    Windows 用户名 / 内网 IP 段：**零命中**；
