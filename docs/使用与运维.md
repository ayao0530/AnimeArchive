# 番剧归档助手 · Anime Archive Helper（本机运维篇）

> **归档器 + 离线媒体库 二合一**的 Windows 本地单机工具。
>
> 扫描目标文件夹**以外**的所有视频文件与文件夹 → 识别同一部番剧 →
> 把名称归一化为**官方中文名**（以 **Bangumi** 为准）→ 按**首播年份 / 月份**剪切到
> `{目标文件夹}/{年份}/{月份}/{官方中文名}/`；并对归档结果建立本地索引，
> 提供一个**可随时打开的离线网站**用于浏览、检索、图表、播放与撤回。

需求与设计的唯一事实来源：`docs/需求与设计文档.md`（v0.5）；
实施指令与验收清单：`docs/实施提示词.md`。
静态交互基线（**未被修改**）：`demo/index.html`。

## 4. 一键启动 / 关闭

| 操作 | 方式 |
| --- | --- |
| **一键启动** | 双击 `server\bin\start.vbs`（或 `start.bat`）→ **无控制台黑框**启动服务并自动打开浏览器 |
| 桌面快捷方式 | 先双击 `server\bin\create-shortcut.vbs`，之后双击桌面的 `AnimeArchiveHelper` |
| **一键关闭** | 网页右上角 **「⏻ 关闭服务」**，或双击 `server\bin\stop.bat`（无残留进程） |
| **关闭网页** | 关掉**最后一个**网页后服务会**自动退出**（默认开，可在「⚙ 设置 → ④ 关闭网页时自动关闭服务」里关掉） |
| 开机自启 | ❌ 不设置，按需手动启动 |

服务默认监听 **`127.0.0.1:9999`**；端口被占用时自动 `+1` 并写回 `server\data\config.json`。

> **`start.vbs` 已经发现服务在跑**（避免起第二个实例把端口挤到 9999+1）→ 这时它**只打开网站首页**
> `http://127.0.0.1:<port>/`，不会再打开 `/api/health` 那个 JSON 接口（那是脚本探测用的，见 #22 变更）。

**「关闭网页即关服务」的几个细节**（默认开启）：

- **有任务在运行时**先弹浏览器原生的「确定要离开吗」二次确认；确认后服务端会先**停止归档**
  （不再取新条目，已在搬的那几个先跑完，避免 NAS 上留半截文件）再退出。下次打开页面会提示
  「上次归档未完成」，点 **▶ 继续归档** 接着跑即可（已搬过去的自动跳过）。
- 判定方式是**一条 SSE 长连接**（`GET /api/page/watch`）：**连接断开 = 页面没了**。
  所以即使页面是被**强制销毁**的（关掉整个浏览器 / 关掉 VS Code 窗口 / 预览被回收 / 崩溃 ——
  这些场景浏览器**不发** `unload` 事件），服务端也能立刻知道，不会留下「幽灵连接」把自动关闭堵死。
- **刷新页面（F5 / Ctrl+R）不会误关**：服务端留 2.5 秒宽限期，新页面在这段时间内连上就取消关闭
  （服务端下发了 `retry: 1000`，万一是网络抖动，浏览器 1 秒后就重连）。
- **多个标签页**：只有**最后一个**页面关掉才会关服务（关掉其中一个不影响）。
- 想恢复旧行为（关页面后让归档继续在后台跑）：把设置里的 ④ 关掉，或直接改
  `server\data\config.json` 的 `"shutdownOnPageClose": false`。

**未启动服务时**：网站仍可打开并**只读浏览**（索引同时产出 `library.js`，双击 `web\dist\index.html`
也能读取），播放 / 撤回 / 重命名 / 扫描 / 归档按钮自动置灰。

## 5. 使用说明

### 5.1 视图① 归档整理

1. 顶栏填写 **源目录**（NAS 共享根，如 `\\NAS\Media`）与 **归档根目录**（如 `\\NAS\Media\已看\Anime`），
   会自动记住上次输入**并写回服务端配置**；扫描时**严格排除归档根目录及其所有子目录**。
   > **目录会自动创建吗？**
   > - 归档根目录（`已看\Anime` 本身）**不会自动创建**：若不存在，界面顶部会给出橙色提示条 +
   >   「➕ 立即创建该目录」按钮，执行归档的二次确认弹窗也会阻断并提示先创建。
   >   这样做是为了避免 NAS 断开时把文件移到一个错误位置；创建动作必须由你显式点击。
   > - 归档根目录**内部的** `{年份}\{月份}\{番剧名}\`、`SP\`、`OP&ED\`、`_未识别\`、`_待确认\`
   >   会在执行归档时**自动逐级创建**，无需手动建目录。
2. 点击 **`↻ 扫描并生成方案`** → 实时显示扫描进度、归一化进度，完成后得到 **dry-run 归档方案**。
   归一化会**自动**使用三级本地策略 + 两层网络佐证（详见 5.1.1），你不需要额外操作。
3. 左栏「原始文件区」按组展示 `原始名 ➜ 官方中文名`、置信度、匹配层级、数据来源与目标路径；
   右栏「归档结果区」树形展示 `年份 / 月份 / 番剧 / SP·OP&ED / 文件`，**两侧悬停/点击双向联动高亮**。
4. 按需处理：
   - **⚙ 处理冲突**（目标已存在同名）：二选一 **自动重命名 (1)** / **跳过**（❌ 无「覆盖」）；
   - **🔎 确认名称**（置信度 < 0.90）：**快速选择**（下拉框 + 搜索，见下） / 候选列表 / 手动输入 / 修正首播年月 / **写回别名表** / 暂不处理 → `_待确认/`；
     弹窗内可勾选「同时应用到其它 N 个同名（同季）分组」；
     > **「快速选择」是一个不占地方的下拉框**：平时只占一行，点一下（或直接输入）才浮出候选面板。
     > 候选同时来自 **本次归档方案**（文件夹还没创建也能选，标 `本次方案`）与 **归档目录里已存在的**（标 `已归档`）。
     > 因为首次使用时归档目录里一个番剧文件夹都还没有，只看「已归档」的话这个框等于没用。
     > 输入番剧名或年份即可实时过滤这两份名单。
   - **☑ 多选批量确认**：卡片左侧复选框（或状态栏「☑ 选择筛选结果」）选中多个分组 → 底部出现批量操作条 →「🔎 批量确认名称」一次性把同一个名称与年月应用到全部选中项；
   - **↗ 单独调整（文件归错组）**：展开分组后，在某个文件行的 **`↗`** 按钮上把这**一个**文件/文件夹拆出来，
     单独指定「番剧名 + 首播年月」（弹窗里同样可以「从已归档文件夹中选择」）。原组的其它文件不受影响，
     被调整的条目会显示 `↗ 已单独调整` 标记，并提供 **`↩` 取消调整** 让其回到原分组；
   - **↗ 批量分开归档（一批文件整体归错组）**：整组都被认错时不必一个一个点——
     展开分组后用文件列表上方的 **`全选`** 勾选多个条目（也可逐个勾），
     在提示条上点 **`↗ 批量分开归档（N）`**，填一次「番剧名 + 首播年月」即可把这 N 个条目一起拆出去。
     > 多个条目指向**同一目标**时会自动汇成**一个**分组，不会散成一堆单文件卡片；
     > 拆出的分组底部提供 **`↩ 取消调整（N 项）`**，一次把整批退回原分组。
   - **文件行显示「创建 / 修改」两个时间**：每条文件后面跟两个时间，鼠标悬停有完整说明。
     > 两个时间在 NAS 上含义完全不同：**创建时间**是文件生成 / 拷入当前位置的时间
     > （批量拷入时整批一样，参考价值有限）；**修改时间**是文件自身的时间，
     > 通常就是这一集的发布时间 —— 它**参与置信度加权**（`🕒` 时间线索），所以用蓝色区分。
     > 旧扫描结果没有创建时间，会显示 `—`，重新扫描一次即可。
   - **🔍 查 Bangumi（弹窗里直接搜番剧）**：两个弹窗都内置了 Bangumi 在线检索，
     输入名称（**简繁皆可，繁体会自动转成简体再检索**）→ 选一条 → 自动填好番剧名与首播年月，
     **不必再另开浏览器去 bgm.tv 查**。输入 2 个字以上会自动检索（600ms 去抖），也可按回车立即搜。
   - **未识别**（无法解析番剧名）：可指定名称，或勾选后移入 `_未识别/`（绝不误归档）；
   - **✏️ 改目标文件夹名**：只改方案中的**番剧文件夹名**，不影响源文件。
5. 点击 **`▶ 执行归档`** → **二次确认弹窗**（显示将移动的项数与体积）→ 进度条 → 结果统计与变更日志。
   归档完成后**自动重建媒体库索引**。
6. **`↩ 撤销整批`** 可把本批次全部移回原位。

#### 方案记忆（人工确认不会被重新扫描冲掉）

每次人工操作（确认番剧名、暂不处理、处理冲突、改目标文件夹名、`↗` 单独调整）都会**自动记入本机方案记忆**
（`localStorage`，按「源目录 + 归档根目录」分组保存）。之后**重新扫描时全部自动恢复**：

- 顶部出现绿色提示条 `📌 方案记忆：已自动恢复 N 个分组的确认结果、M 个单独调整`，并写入变更日志；
- 分组卡片上的提示为 `已从方案记忆恢复该确认结果`，无需再次点选；
- 需要从头开始时，点提示条或状态栏的 **`🧹 清除方案记忆`**（仅清本机记忆，不动任何文件）。

> 方案记忆是「界面/方案层」的便利功能，与 `server\data\aliases.json`（L1 名称归一化别名表）互不影响、可以同时使用。

#### 5.1.1 提高归一化准确率（网页检索 + 文件修改时间）

罗马音 / 英文文件名（`Hataraku Saibou!!`、`Sousou no Frieren`）与 Bangumi 的日文条目之间
**算不出字符串相似度**，过去只能给「相关度第 1」打一个先验分，于是大量条目停在「待确认」。
现在归一化流程是：

```
预处理 → ① L1 本地别名表
        → ② L2a Bangumi 在线查询
        → ② L2b 前置网页检索：把罗马音/英文还原成日文原名或中文译名 → 回查 Bangumi
        → ③ L3 模糊匹配（+ 严格键 + 季数 + 文件修改时间）
        → 置信度判定 → 兜底
```

**A. 前置网页检索（把标题"翻译"回日文原名）**

| 检索源 | 是否需要 Key | 说明 |
| --- | --- | --- |
| **Google Programmable Search** | 需要（可选） | 在「⚙ 设置」里填 API Key + 搜索引擎 ID 后启用；免费额度 100 次/天 |
| **Wikipedia**（en / ja 交叉取标题） | ❌ 不需要 | 可用性最好，一条请求就能同时拿到**日文原名 + 中文译名** |
| **Kitsu** | ❌ 不需要 | 直接给出 `ja_jp` / `zh_cn` 标题 |
| **AniList** | ❌ 不需要 | 2026-09 官方一度临时停用，故仅作补充 |
| **Jikan / MyAnimeList** | ❌ 不需要 | 上游偶有不稳定，作为兜底 |

- 多个源**并行发起**，但**不是"谁先返回用谁"** —— 按可信度取（Google > Wikipedia > Kitsu > AniList > Jikan）：
  Kitsu / MAL 的搜索是**子串匹配**，`5Hanayome` 会被匹配到 `瀬戸の花嫁`（Seto no Hanayome）这类只共用了 `Hanayome` 的作品；
  Wikipedia 的 `generator=search` 基于标题与重定向，命中质量明显更好，因此必须等它表态再定夺。
- 只有「看起来像罗马音/英文」且「直接查 Bangumi 达不到自动归档阈值」的名称才会触发，命中后缓存 30 天；
- 拿到还原名后**回查 Bangumi**，此时两边都是同语言，可以做**严格键比对**：
  严格键只去掉空白与 `_`，保留 `!` `∬` `∽` `数字` 等后缀，因此能区分
  `はたらく細胞` / `はたらく細胞!!`、`五等分の花嫁` / `五等分の花嫁∬`
  —— 而普通的别名键（去标点）会把它们压成同一个键，这正是「续作被并到一起」的根因。
- 若还原名指向的条目**首播晚于文件时间**（首播晚于下载＝不可能），说明这个还原名基本是错的 → 丢弃它退回文件名自身证据。

> 不配置 Google 也完全可用：默认走免费的 Wikipedia / Kitsu 等，效果等价。
> 所有检索只发送**番剧名称**，不发送文件名、路径或文件内容。

**B. 文件修改时间作为置信度参考**

文件的修改时间 ≈ 你把它下载 / 拷进来的时间，于是：

- 番剧**首播时间不可能晚于**文件时间 → 晚于的一律重罚（−0.30），不可能被选中；
- 与文件时间**同季**（±4 个月）→ **+0.14**（当季追番）；
- 同年 / 隔一季 → +0.10；一两年内补番 → +0.05；再久 → 不加分（老番补看很常见）。

这对**续作 vs 第一季**特别有效：`Hataraku Saibou!!` 的文件时间是 2021-02，
第 2 季（2021-01）加分、第一季（2018-07）不加分，于是能正确归入「工作细胞！！」。

**C. 当"一个名字对多季"时怎么办**

网页检索给出的往往是**整个系列**的标题（`Hataraku Saibou!!` → `はたらく細胞`），
它同时命中第 1 季与第 2 季 —— 此时名称证据**无法区分季数**，
系统会把这几条的名称证据统一压到 0.86，再让**文件时间**决出唯一一条越过自动归档阈值；
如果既没有时间线索又无法区分，就如实落到「待确认」，绝不猜。

界面会显示判断依据，便于复核：

- 分组卡片上的 `🔎` 命中方式（如「网页检索（Kitsu）还原标题「はたらく細胞BLACK」→ Bangumi 精确命中」）
- 分组卡片上的 `🕒` 时间线索（如「文件时间 2021-02 · 首播 2021-01 与文件时间同季」）
- 人工确认弹窗里，候选列表会标注 `✅ 网页还原名精确命中` / `⚠ 首播晚于文件时间` / `🕒 与文件时间同季`

> ⚠ 纯模糊（"碰巧像"）的候选在已存在权威名称证据时，**不允许**靠时间加分越过自动归档阈值，
> 必须落到「待确认」——这条保护防止错误答案被自动移动。

#### 5.1.2 秒开：直接载入上次扫描结果（不必每次打开都重新扫描）

每次**成功扫描并生成方案**后，结果会存成**两份快照**：

| 位置 | 作用 |
| --- | --- |
| `server\data\last-scan.json` | 权威副本，可在机器间共享 |
| 浏览器 `localStorage` | **本机备份**，服务端副本丢失/读不到时兜底 |

下次打开页面时会**自动载入**，不再重新扫描：

- 顶部显示蓝色提示条 `📂 已载入上次扫描结果 · 09-12 16:29 · 1 组 / 2 个文件`，并提供 **`↻ 重新扫描`** 按钮；
  若用的是本机备份会标注 `（本机备份）`；
- 载入后只做一次**轻量的方案重算**（`POST /api/plan`）：重新计算目标路径与冲突状态、并叠加方案记忆，
  这一步不读源目录、不查 Bangumi，通常 1 秒内完成；
- 只有点击 **`↻ 扫描并生成方案`**（或提示条里的 `↻ 重新扫描`）才会真正重新扫描；
- 目录没变才生效：若源目录/归档根目录与快照记录的不一致，会忽略快照并提示「请点击扫描」；
- **执行归档之后不会清空快照，而是"裁剪"**：把已移动成功的条目从列表里去掉、保留剩下的。
  所以「归档了一部分 → 关掉 → 再打开」时，剩下的待处理项**立刻就在**，不必重扫；
- **撤回之后**快照标记为「⚠ 之后做过撤回，建议重新扫描」（源目录又变回来了，列表已不完整）；
- 全部归档完成后再打开，会显示 `📂 上次扫描结果里的文件已全部归档完成（…）` + `↻ 扫描新文件`，
  而不是一句让人困惑的「尚未扫描」；
- 服务未启动时点「⏻ 启动服务」重连，也会走同一条载入流程（不会因为"先开页面后启服务"而丢结果）。

**「对照列表」视图**提供完整的 `原路径 ➜ 归档后路径` 全量对照。

#### 5.1.3 并行扫描：NAS 上快 2~3 倍

NAS / SMB 上**每一次 `readdir` / `stat` 都是一个网络往返**（典型 5~30 ms），
而逐个文件串行处理会让「8000 个文件」变成「8000 次往返排队」。
因此扫描、索引与归一化全部改为**有界并发**（默认 10 路）：

| 阶段 | 改动 |
| --- | --- |
| 目录遍历 `scanner.ts` | 同一层的条目并发处理，**结果按原目录顺序重组**（顺序稳定、断点一致） |
| 子目录度量 `fsx.ts` `measureDir` | 目录内所有文件的 `stat` 并发；顺带返回 `hasDirectVideo`（省掉一次额外遍历） |
| 媒体库索引 `indexer.ts` | 文件 `stat` 与子目录递归并发，全局总阀 10 |
| 归一化 `grouper.ts` | 不同番剧名并发查询（同名去重后只归一化一次），并发数 = `scanConcurrency × 0.6`，避免打爆 Bangumi 的 3 QPS 限流 |

> 说明：Node 是单线程的，这里的「多线程」是**异步并发**（同时在飞行中的 I/O 请求数）——
> 对「延迟大、吞吐不低」的网络盘才是正确的提速方式；真正的多线程反而会因锁竞争变慢。
> 并发写入 `bangumi-cache.json` 已通过写队列串行化，不会丢写入。

**实测（本机 NAS，8000+ 个视频 / 50 个文件夹）**：

| 并发度 | 扫描耗时 |
| --- | --- |
| 1（原串行行为） | 19.3 s |
| **10（默认）** | **6.9 s** |
| 20 | 6.7 s |

即默认提速 **2.8×**；并发度可在「⚙ 设置 → 扫描并发度」调整（建议 NAS 8~16，本地磁盘 4~8）。

> 因为并发只是把**同一个任务**提前发起，扫描结果与串行完全一致（已用自检 19/19 回归验证）。

#### 5.1.4 归一化提速：别再重复算 `aliasKey`

除了目录 I/O，第二个瓶颈在**纯 CPU**上的 L3 本地模糊匹配：
它对「每一部番剧 × 别名表每一条」都要算一次相似度（实测 743 × 2862 ≈ **210 万次**），
而 `similarity()` 内部会对两边都跑一遍 `aliasKey()` ——
那是 10 步、二十多个正则的 `preprocess()`，单次约 **40µs**，光这一步就要烧掉一分多钟。

修法：`Store` 在别名表变化时**预先算好**每条别名的归一化键（`AliasItem.key2`），
归一化时直接拿现成的键算相似度（`similarityKeyed()`）。

| 阶段 | 优化前 | 优化后 |
| --- | --- | --- |
| 本地 L3 归一化（8286 文件 / 743 组） | 77.3 s | **6.0 s** |
| 整轮扫描（含联网归一化 + 生成方案 + 存快照） | 137 s | **25 s** |

同时把 `aliases.json` / `bangumi-cache.json` 的读写改成**常驻内存 + 合并写盘**：
以前每归一化一部番剧都要把整个文件读出来 parse 再写回（各 1~2MB），一次扫描重复上千次；
现在只在扫描结束后落盘一次（关服务时也会强制落盘）。

> ✅ 等价性已实测：同一份真实数据（8286 文件）在新旧代码下输出的 **743 个分组完全一致**
> （对比了每个分组的中文名 / 年月 / 文件集合），自检 19/19 也保持通过。

#### 5.1.5 多季作品：优先匹配**已经归档好的那个文件夹**

**症状**：`[ANi] 小書痴的下剋上 為了成為圖書管理員不擇手段！領主的養女 - 21 …`（第四季）
却被自动归到了**第一季**文件夹 `小书痴的下克上 〜为了成为图书管理员而不择手段〜`（2019/10），
而第四季自己的文件夹 `… 领主的养女`（2026/04）本来就在归档区里躺着。

**根因**（实测定位）：别名表里有一条**脏记录** —— 第一季的条目把第四季的名字也当成了自己的别名。
它是旧版写入产生的（确认第一季时，整组的 `rawName` 一起写进了 `aliases[]`），
于是第四季文件名会**直接精确命中**这条记录：`matchLevel=L1`、`dataSource=manual`、**置信度 1.0**，
后面的在线检索与模糊匹配**完全没有插手的余地**。

**两道修法，一读一写：**

1. **读时复核（`normalizer.ts` · 更具体者胜）**
   L1 精确命中后**再复核一次**：如果存在一个名字——它**更长**（= 更具体）、
   且与文件名的相似度**明显更高**，就采纳更具体的那个。
   两个证据源：别名表里的官方名，**以及归档区里已经存在的番剧文件夹**
   （用户已经手工确认过的结果，可信度最高）。

   四条判据同时成立才替换（宁可漏改，不可错改）：

   | 判据 | 实测值 |
   | --- | --- |
   | 候选键**严格更长** | S4 键 28 字 > S1 键 23 字 |
   | 候选键**包含**当前键（真正的「名字 + 后缀」型扩展） | `S4键.includes(S1键) = true` |
   | 候选与文件名的相似度 ≥ `0.8` | 第四季文件对 S4 = **0.915** |
   | 候选比当前命中至少高 `0.03` | 0.915 − 0.822 = **+0.094** |

   > 为什么必须加「包含 + 绝对值」两道闸：相似度是
   > `0.5×TokenSet + 0.3×JaroWinkler + 0.2×编辑距离`，**对无关名字也会给分** ——
   > `Full Dive` 对 `CLANNAD` 能得 **0.179**，而它对真正命中的那个名字是 **0.000**；
   > 只比"谁更高"就会把 CLANNAD 抢进来（实测把 A5 用例带崩）。
   >
   > 反向也安全：第一季文件对 S1 = 0.909、对 S4 = 0.823（**−0.086**），不会被抢；
   > 已经精确命中正确名字时相似度≈1.0，没有候选能高出 0.03。

2. **写时护栏（`store.ts` · `upsertAlias`）**
   写入别名时，若某别名**更长且与官方名的键相似度 ≥ 0.8**，判定为「另一季的标题」，
   **拒收**（既不入索引也不进 `aliases[]`）——从源头堵住脏数据的产生。
   这里不能用「键包含」：繁简与装饰符会让包含关系失效
   （`…不擇手段！領主的養女` 与 `…〜而不择手段〜` 差着 `〜` 和 `而`，键里互不包含）。

**成本（实测，不是估算）**：复核只在 L1 命中时跑，且对每个**不同**标题只跑一次（分组层已去重）。

第一版实现踩了本仓库 5.1.4 已经记录过的老坑 —— 在热循环里现场跑 `aliasKey`：

| 实现 | 每次复核 | 一次扫描（约 750 个标题） |
| --- | --- | --- |
| 遍历 3600+ 条**键**、现场算键 | **229 ms/名字** | +172 s（整轮才 25 s） |
| 遍历 700+ 个**官方名**、用预计算键 | **0.62 ms/名字** | **+0.46 s** |

修法两条：`Store` 另建 `zhIndex`（官方名 → 预计算键 `key2`，
按官方名去重后 3619 → **721** 个），热循环里只做「长度比较 + `String.includes`」；
已归档文件夹那 700 多个键按数组对象用 `WeakMap` 缓存，一次扫描只算一次。

> 净开销实测 **0.28 ms/名字 ≈ 0.21 s / 次扫描**（对照整轮扫描 25 s，约 1%）。

**实测验证**（真实数据）：

```
扫描日志：ℹ 已载入 709 个已归档番剧文件夹，多季作品会优先匹配已有文件夹
该文件 →  2026/04/小书痴的下克上 〜为了成为图书管理员而不择手段〜 领主的养女/…✅
反向：第一季文件仍归 2019/10/小书痴的下克上 〜为了成为图书管理员而不择手段〜 ✅
```

#### 5.1.6 执行归档：并发 10 + 断点续传 + 可随时停止

**并发**：搬文件默认 **10 路并发**（与扫描共用「⚙ 设置 → 扫描并发度」，上限 32）。
NAS 上单次移动是一次网络往返（跨卷时还要复制），串行搬 8000 个文件会慢到没法用。

**断点续传**：页面关掉/刷新**不等于任务停了** —— 任务跑在本地服务里。
服务端把执行进度写在 `server\data\execute-state.json`，所以：

- 重新打开页面 → 顶部出现紫色提示条 `🔄 归档正在后台进行 · N / M（xx%）`，每 1.5s 接上实时进度；
- 如果服务端也断了（没跑完）→ 黄色提示条 `⏸ 上次归档未跑完：还剩 N 项` + **`▶ 继续归档`**；
  直接再点一次「执行归档」就行 —— 已经搬过去的条目会被**自动识别并跳过**，
  既不会重复搬，也不会被当成失败。

> 配套：每搬完一条就**追加一行日志**（`logs\batch-<id>.jsonl`）。
> 以前是整个批次结束时才写一次日志，一旦中途被关掉，那些已经搬走的文件就失去了撤回依据。

**安全护栏（P0）**：执行时会校验「目标路径是否真的在归档根目录内」，不在就拒绝并报错。
这条护栏就是下面那个 UNC bug 换来的教训 —— 宁可整批停下，也不能默默把文件搬到别的机器上。

**停止归档（`⏹ 停止归档`）**：进度弹窗与顶部进度条上都有这个按钮，点了**立即不再开始新文件**。

- 语义是「不再取新条目」而不是「立即硬断」：**已经在搬的那几个（最多并发数 10 个）会先跑完**，
  因为半途中断会在 NAS 上留下复制到一半的碎文件（而源文件还在，会造成「一半在一半在」的错觉）。
- 停止后 `execute-state.json` 写 `stopped: true`，顶部变成黄色条：
  `⏹ 已停止归档：已处理 N / M 项，还剩 K 项未处理`，并直接提供
  **`▶ 继续归档`** 与 **`↩ 撤销整批`** 两个按钮 —— 继续、撤回都随时可用。
- 停止不会丢掉日志：批次日志照常落盘（`batch-<id>.json`），所以「撤销整批」能 **只撤这一批**。

> ⚠ 批次号 = 时间戳（秒）+ **随机后缀**。不能只用时间戳：用户「点停止 → 马上点继续」时
> 两批很可能落在同一秒，同号会让后一批的日志**覆盖**前一批，于是「撤销整批」会撤到错误的那一批上。

**迁移失败自动重试**：单条移动失败会**自动重试最多 3 次**（共 4 次尝试，退避 300ms / 800ms / 1.5s），
NAS 上偶发的 `EPERM` / 网络瞬断基本都能重试成功。

- 重试**只在同一条目标路径上**做：唯一名（`(1)`）只算一次。
  否则「第一次其实已经复制成功、只是删源失败」的条目会在重试时再去找 `(2)`，在 NAS 上堆出重复文件。
- 源文件已经不在时不再重试（重试没有意义）。
- 4 次都失败 → 记进批次日志，**同时**写进 `execute-state.json` 的 `failedItems`，
  顶部出现红色提示条 `⚠ N 项迁移失败：已自动重试 3 次仍未成功，源文件原样保留、未移动`，
  带「📜 查看日志」和可展开的**完整路径 + 失败原因**清单，等你后续人工处理（点「知道了」才消掉）。

#### 5.1.7 列表动态加载（千组也不卡）

一次扫描出来的分组动辄几百个、文件行上千条，全部塞进 DOM 会让页面滚动/输入都卡。现在两栏都是按需渲染：

| 位置 | 策略 |
| --- | --- |
| 左侧「原始文件区」 | 先画 **40 组**，底部「加载更多」再追加 40；卡片内条目超过 **40 行**时先只画 40 行，点「显示全部」才全画 |
| 右侧「归档结果区」 | 分组数 > 60 时**月份默认折叠**（点月份行才展开），展开时才真正创建文件行节点 |

实测（742 组 / 8286 文件）：首页 DOM 节点从 **53,782 → 7,809**（右侧树从 8286 行 → 0 行）。

> ⚠ 折叠时必须是「不渲染」而不是加个 `.hidden`（`display:none`）—— 后者节点照样建，一样卡。

#### 5.1.8 二次整理：三个地方都能「发现归错了就改」

归错位置了不用回原始文件区重来 —— 下面三个地方每一条都能点 **`↗`** 改归档目标：

| 位置 | 操作对象 | 效果 |
| --- | --- | --- |
| 左侧「原始文件区」卡片 | 单个 / 批量勾选的文件 | **改方案**（记入方案记忆） |
| 右侧「归档结果区」树形视图 | 每个文件行 / 番剧名那一行（整组） | 已归档的**真实移动**；没搬的只改方案 |
| 右侧「对照列表」 | 每一条 | 同上（看「原路径 ➜ 归档后路径」最直观） |
| 「② 媒体库」文件行 | 单个文件 | **「↗ 移动」真实移动**（不必先撤回再归档） |
| 「② 媒体库」番剧卡片头部 | **整部番剧（N 集一起）** | **「↗ 批量移动」真实移动** |

为了能判断到底该「改方案」还是「真移文件」，前端会拿媒体库索引里的 `originPath`（归档前的原始路径）
反配对：

- 命中 → 文件**真的已经在归档目录里** → 走 `POST /api/library/move` 真实移动，然后重建索引；
- 没命中 → 只是**方案**（还没执行过归档）→ 走方案记忆，不动磁盘。

一次操作里两者可以混在一起（比如点番剧名那一行的整组 `↗`），各自走各自的路，弹窗也会如实写清楚这次到底会不会动磁盘。

后端约束（`server\src\core\libraryMove.ts`）：只能在归档根目录**内部**移动；目标目录不存在则逐级创建；
目标已有同名文件则自动加 ` (1)`，**绝不覆盖**；每次移动都记入日志。

**移走之后自动清理空目录**：把一集挪走（尤其是把整部番剧挪空）之后，
`2023\07\某番剧\` 会留成一个空壳，月份/年份目录也可能跟着空掉。现在会自动
**从被移空的那一层往上逐级删**，直到遇到非空目录或归档根为止：

- 只删**归档根目录内部**的目录，**绝不动归档根本身**
  （注意 `isInside` 是**含自身**语义，光靠它挡不住「把根也当成一层」，还必须有显式比较 —— A35 锁住这个边界）
- 只有 `readdir` 结果为空才删（有隐藏文件也算非空）
- 一路**遇到非空立刻停**，不会误伤兄弟目录
- 删掉什么会写进日志并在界面提示（这是个「删」操作，不能默默做）

**为什么要单独做一个批量接口**（`POST /api/library/move-batch`）：
单文件接口每搬一条就**重建一次媒体库索引**，整部番剧 100 集就是 100 次全量重建；
批量版只在结束时重建一次（而且 `moved === 0` 时干脆不重建）。
失败隔离：单条失败（文件被删/被占用）只计入 `failed` 并报给你，**不中断整批**；
目标与当前位置相同时计为 `unchanged`（而不是报错）—— 你要是把一部番剧「移到自己」，
提示会是「它们本来就在这个位置，没有文件需要移动」。

> ⚠ 归档结果区里的 `↗` 只对**已经归档过**的文件变成「真实移动」。如果归档区还是空的（或者服务端索引没重建），
> 每一行都只能改方案 —— 这是对的，因为确实还没有文件可移。

> 顺带修一个坑：`vite build` 会**清空 `web\dist`**，连里面的 `data\library.json` 一起删掉，
> 于是「重建一次前端 → 媒体库变空」。现在索引会额外写一份到 `web\public\data`（会被原样拷进 dist）。

#### 5.1.9 繁体文件名：检索前必须先转简体

文件名里的繁体标题**不能原样拿去 Bangumi 检索** —— 后果不只是「搜不到」，
而是会**命中错误条目**（实测）：

| 检索词 | 首条结果 | 结论 |
| --- | --- | --- |
| `孤獨搖滾`（繁） | 透明的孤独 | ❌ 不相干的另一部作品 |
| `孤独摇滚`（简） | `ぼっち・ざ・ろっく！` / 孤独摇滚！ | ✅ |
| `咒術迴戰`（繁） | 呪術廻戦 4D 电影版 | ❌ |
| `咒术回战`（简） | `呪術廻戦 死滅回游 前編` | ✅ |
| `佐賀偶像是傳奇 捲土重來`（繁） | ゾンビランドサガ（**第一季**） | ❌ |
| `佐贺偶像是传奇 卷土重来`（简） | ゾンビランドサガ リベンジ（第二季） | ✅ |

所以 `buildBangumiQueries()` 会先生成**简体检索词**：

- **不含假名**（= 中文标题）→ **简体优先**，查不到再退回原文；
- **含假名**（= 日文原名）→ **原文优先**，因为日文汉字与繁体同形，
  把 `進撃の巨人` 转成 `进击の巨人` 反而会让检索变差。

> 底层字表**换成了完整的「繁 → 简」表**（由 OpenCC `TSCharacters.txt` 生成的 `server\src\util\t2s-data.ts`，共 2966 条）。
> 早期是手工挑的「高频字表」，缺了几百个常用字（給 宮 僅 擇 擊 捲 搖 換 檔 剋 傳 迴 獨 滅 …），
> 这才是上面那些错配的根源。
> 本项目坚持零运行时依赖，所以字表是**内嵌数据**（生成结果入库）而不是依赖包，依旧完全离线可用。

### 5.2 视图② 媒体库（目标文件夹）

- 浏览：`年份 → 月份 → 番剧卡片 → 子目录(SP / OP&ED) / 剧集行`
- **四层全部默认折叠**：年份 / 月份 / 番剧卡片 / 子目录，逐层点开
  （一个年份动辄上千个文件，折叠时**不建 DOM**；一搜索则自动展开命中项）。
  实测 2026 年：初始只渲染 9 个年份行、**245 个 DOM 节点**；逐层展开到子目录才 940 个
  （对比：全部展开的年份会建上万个节点）
- **检索（仅作用于媒体库）**：番剧名 / 别名（中·日·英）/ 文件名，支持 `year:2022` `month:10` `ep:01` `type:sp`
- **多选 + 批量移动**：文件行左侧勾选框；番剧卡片头 / 子目录行各有一个**三态「全选」**
  （全选 / 部分 / 未选）。勾选后底部浮出「☑ 已选中 N 个文件（X GB）」条 →「↗ 移动选中 N 个」
  把选中的文件**一次性**移到另一部番剧。
  - 走 `/api/library/move-batch`（**批量接口**：只重建一次索引；目标同名自动加 ` (1)`，绝不覆盖）
  - 选择集**跨卡片、跨年份**都能攒（只存文件路径，不存对象 —— 搬完索引会重载）
  - 搬完**自动清空勾选**；失败则保留选择，方便直接重试
  - **执行期必须有反馈、并且锁住界面**（踩坑：以前点一下弹窗立刻关，NAS 上搬几 GB
    要几十秒，界面一点动静都没有 → 用户以为没生效 → 再点一次 → 重复移动）：
    弹窗**保持打开**，显示「⏳ 正在移动 12 个文件（3.9 GB）…已用 N 秒，请勿重复点击」
    （秒表在走 = 还活着），两个按钮全部禁用；搬完再显示「正在刷新媒体库…」然后才关闭
  - 🔴 **刷新失败必须看得见**：以前只写一行日志，列表继续显示旧数据 → 用户以为没生效 → 重复操作。
    现在 `loadLibrary()` 失败会**重试一次**，仍失败就在列表顶部显示红色提示条
    「⚠ 索引刷新失败（服务可能正忙）」+「↻ 重试」按钮
  - 单文件「↩ 撤回」/「✏️ 改名」也走全局忙碌遮罩（同样防止重复点击）
  - 实测：1123 行全展开时勾一下 **46 ms**（文件行做了 `memo`）
  - **入口必须就地**：光在底部浮一条不够（用户实测反馈「勾了但找不到怎么只移动勾选的」）——
    所以勾选后**卡片头会直接多出一个带数量的按钮**，列表顶部的说明也写明用法
  - 底部条用 `createPortal` 挂到 `document.body`（`.panel` 是 `overflow:hidden` 的滚动容器，
    不再依赖「fixed 不受祖先影响」这一点）
  - **各个「移动」按钮的语义必须分清**（同名撞车踩过坑：用户勾了 1 个文件却点了同名按钮，
    结果整个文件夹 24 个文件被搬走）：

    | 位置 | 文案 | 作用范围 |
    | --- | --- | --- |
    | 番剧卡片头 | `↗ 整部移动（N）` | 这一部番剧的**全部**文件 |
    | 番剧卡片头（有勾选时才出现） | `↗ 移动选中的 N 个`（强调色） | **只**这一部里勾选的那些 |
    | 子目录行 | `↗ 移动整个目录` | 那个子目录（含里面所有文件） |
    | 文件行 | `↗ 移动` | **只这一个**文件 |
    | 底部选择条 | `↗ 移动选中 N 个`（强调色） | 跨卡片的**全部**勾选项 |
- **图表**：**年份一行，点年份整行就地展开该年的月份行**（只列**真实存在**的月份，不留空的 12 个月；默认展开最新一年）
  × 两种度量 **番剧数量 / 占用空间**（工具栏那组 `番剧数量 | 占用空间`）：
  - 展开的月份行缩进 + 柱子淡一点；年份行悬停高亮、键盘回车/空格也能展开
  - 柱状图与下方「年份/月份明细」共用同一份行数据（数字必然一致）；明细是 `N 部 · M 集 · K 个文件` + 体积
  - **明细**：点**月份整行**展开该月的番剧名单（竖表：`名称` + `N 集`，跨季重复计入的标 `跨季`），
    **默认折叠**，再点整行收起；名单条数与同行「N 部」必然一致。
    年份行**不做**这件事（它保持「点整行展开月份」）—— 两个展开行为分层不打架
    - **点名单里的番剧名 → 左侧媒体库直接跳到那个文件夹并高亮**（同时把其他已展开的年份/月份折叠起来，
      只留目标这一条链路；若检索框里有词会先清空，否则树被过滤掉就找不到目标）
  - 年份统计**不含** `_未识别` / `_待确认`；手建目录没有月份时显示为 `YYYY-未知`
  - 总览数字卡片 6 张（番剧总数 / 文件总数 / 总占用空间 / 可撤回 / 特殊目录 / 覆盖年份）
- **图表统计口径**（三条规则，标题下方会写明「已排除 N 部（≤3 集）」等）：
  1. **集数** = 顶层**视频**文件数 + 子目录数（每个子目录算 1 集）。**不是文件数** ——
     `[FLsnow][Star-Detective_Precure][05][1080p]` 这种多文件发布目录只算 1 集；`SP` / `OP&ED` 不算集数。
     番剧卡片上的「N 集」也按这个口径（悬停可看真实文件数）。
  2. **集数 ≤ 3 的番剧不纳入统计**（零散 / 不完整的归档，例如只有 2 集的那部，会把月份分布带偏）。
  3. **集数 > 14 且在 1/4/7/10 月播出的番剧，按季度重复计入**（半年番在下一季仍在播，当季统计不该漏掉它）：
     `16 集 4 月首播 ⇒ 4 月与 7 月都计入`；跨几季 = `ceil(集数 / 14)`（16⇒2、24⇒2、36⇒3，最多 4 季，可跨年）。
     ⚠ 起点**不是**季度月的（如 2 月播的常年番）**不做跨季**，按原样只进自己那个月。
     ⇒ 因此月份行的「部数」之和会**大于**年份行（年份桶同一年内同一部只计一次）。
  - 数字卡片里的「番剧总数 / 文件总数 / 总占用空间」是媒体库**真实总量**，不受上面口径影响。
  - ⚠ 还没点过「↻ 重建索引」的**旧** `library.json` 里没有 `stats.airMonths` / `airYears` / `episodes`，
    前端会现场按同一套口径算一遍（实测数字与重建后的索引**逐项一致**），所以不需要为了看统计而重扫 NAS
- **▶ 播放**：调用 Windows 默认播放器（由本地服务执行 `start "" "<UNC 路径>"`）
- **文件行**：集数徐标 · 文件名 · 大小 · **修改时间**（固定宽度 `2023-07-08 10:45` + 等宽数字，整列对齐）
  · `▶ 播放 / ↩ 撤回 / ↗ 移动`
- **文件按集数数字排**（不是按文件名字符串）：同一部番剧常混多个字幕组
  （`[BeanSub&FZSD]…` / `[Nekomoe kissaten]…`），按整串排会把它俩各自排成一堆 ——
  01 后面直接跟 14、而 02 要翻到另一段才出现（用户实测就是这个现象）。
  规则：① 解析得出集数的在前，按数值排；② 同集数按后缀（`24` 在 `24v2` 前）；
  ③ 解析不出的（NCOP / 特典 / 未识别）放最后，按文件名自然序。
  前端渲染（`web/src/utils.ts` 的 `compareByEpisode`）与服务端索引（`server/src/core/parser.ts` 同名函数）
  用的是**同一套规则**（改一处要改两处），并已用 A39 锁定
- **📂 打开文件夹**（番剧卡片）：在文件资源管理器中打开这部番剧的文件夹
  （以前只能自己从 NAS 一级级点进去）
- **↗ 移动 / ↗ 批量移动**：改归到另一部番剧（真实移动，见 5.1.8；移空后的原目录会自动清理）
- **单独子目录行**（如 SP / OP&ED / 整包归档进来的目录）：也有 **`↩ 撤回`** 与 **`↗ 移动`**，
  作用于**整个子目录**（含里面所有文件）—— 子目录在磁盘上就是真实文件夹，可以整体搬。
  撤回按钮会根据索引里的「有无归档记录」自动置灰（比如 `SP` 目录是本工具建的，不是搬进来的，就撤回不了）
- **↩ 撤回**：单文件移回归档前原位置；原位置已有同名文件时自动加 `(1)`
- **✏️**：真实重命名 NAS 上的**番剧文件夹名**（文件名永不改动；年份/月份层级不可改）
- **`↻ 重建索引`**：全量重扫 `已看/Anime` 并重建 `library.json`

> ⚠ `explorer.exe` 有两个会「**静默失败**」的坑，两个都实测确认过（否则窗口根本不出来，而且看不出错在哪）：
>
> 1. **不能传 `windowsHide: true`**（Node 的 `spawn` 选项）：libuv 会因此设
>    `STARTUPINFO.wShowWindow = SW_HIDE`，资源管理器窗口**被创建但隐藏** ——
>    命令成功、`'spawn'` 事件照常触发，屏幕上却什么都不出现。
>    （`cmd /c start` 不受影响，所以「▶ 播放」一直是好的。）
> 2. **`/select` 的引号只能包住路径**：`/select,"<路径>"` ✅，`"/select,<路径>"` ❌ ——
>    而 Node 的 `spawn` 默认正好是错的那种，结果 explorer 解析失败、**静默把「文档」打开**。
>    实现里改用 `windowsVerbatimArguments` 自己拼命令行。
>
> 另外 `explorer.exe` **成功时也返回退出码 1**（历史行为），所以不能靠退出码判成败；
> 但**坏路径必须先自己拦掉** —— 否则 explorer 同样会静默打开「文档」。
> 以上两条都有自检锁住（A32 / A33）。
>
> ℹ 文件行曾经也有一个「📂 打开位置」（选中到具体文件），后来按反馈去掉了 ——
> 文件动辄上千行，逐行给按钮太碎；`POST /api/fs/reveal` 的 `select` 参数仍保留，
> 想恢复随时加回即可。
- `_未识别/`、`_待确认/` 以**灰色分组**展示在页面底部，可播放 / 重命名，不参与图表统计

## 7. 安全原则

1. **默认 Dry-Run**：先出方案，点击「执行」才真正移动。
2. **剪切移动**：源与目标同在 NAS 时直接 `Move`；跨设备自动降级「复制 → 校验 → 删除源」。
3. **不删除任何文件**：冲突只重命名加 `(1)`，绝不覆盖、绝不删除。
4. **全量日志**：每次移动都记录 `fromPath` / `toPath` / 时间戳 / 结果，支持整批撤销与单文件撤回。
5. **失败隔离**：单条失败不中断整批，失败项**保留源文件**并单独记录原因。
6. **NAS 异常保护**：归档前探测归档根目录可写；不可写则中止且**源文件零改动**。
   归档根目录**不会静默创建**（需你在界面上确认「➕ 立即创建该目录」），避免 NAS 断开时移错位置。
7. **仅本机**：服务只监听 `127.0.0.1`，不对外网开放。

> 关于「上次扫描结果」快照：它只是一份**列表缓存**，不含任何写操作。
> 因为可能已经过时，**执行归档前仍会让你在二次确认弹窗里核对项数与体积**，
> 且在执行归档 / 撤回后立即失效；文件有增减时点一下 `↻ 重新扫描` 即可刷新。

## 8. 支持的命名风格

| 风格 | 示例 | 说明 |
| --- | --- | --- |
| 常见新番式 | `[Lilith-Raws] Full Dive - 04 [Baha][1080p][AVC AAC][CHT].mp4` | 字幕组 + 主体 + 集数 + 标签 |
| **顺序方括号式** | `[Airota&Nekomoe kissaten][Yuru Camp S2][02][1080p][CHS].mp4` | 番剧名本身在方括号里也能识别（自动跳过分辨率/语言/容器等元数据块） |
| 文件夹整体 | `[Lilith-Raws] Full Dive - 03 [Baha][1080p]`（目录） | 整个文件夹作为一个单元移动，不拆散内部文件 |
| 续作 / 季数 | `Yuru Camp S2` / `… SEASON 2` / `… 第2季` / `… Part 2` | **严格区分季数**，各自独立文件夹与各自的播出年月，不会全落到第一季 |
| 特殊内容 | `… - SP01` / `… NCOP` / `… NCED` | 分别进入番剧目录下的 `SP\` / `OP&ED\` |
| 字幕组名含 `NC` | `[NC-Raws] xxx - 01.mp4` | **不**判定为无字幕 OP/ED（`NC` 必须是独立标签，如 `[NCOP]` / `- NCOP`） |
| 无法识别 | `[Group] [Unknown] - 01.mp4` | 进 `_未识别\`，绝不误归档 |
| 文件夹名带季数 | `5Hanayome_S2/` | `_` 视作分隔符，识别为「5Hanayome + S02」（下划线属于「单词字符」，不特殊处理会漏掉 `\bS(\d+)\b`） |

## 9. 已知限制（与设计文档一致）

- ❌ 不装 ffprobe → 索引中**不显示时长**
- ❌ 不使用封面图 → 番剧卡片为纯文字 + 📁 图标
- ❌ 不自动重命名文件（唯一例外：冲突时自动加 `(1)`）
- ❌ 不做目录监控 / 常驻后台，改为**手动触发扫描**
- ❌ 不做网页内嵌播放器（只调起系统默认播放器）
- ❌ 不提供「覆盖」冲突选项
- ❌ 不做繁体译名适配（统一简体中文）
- 归一化会访问第三方**公开**接口（Bangumi / Wikipedia / Kitsu / AniList / Jikan）。
  它们偶发不稳定或限流；任一源失败都会被静默跳过、退回其余源或本地逻辑，**不会中断扫描**。
  命中后会缓存 30 天，重复扫描不再联网。
- ❌ 不解析 `library.json` 之外的元数据（不读内嵌字幕 / 章节信息），因此「文件修改时间」是唯一的旁证
- 扫描 / 索引 / 归一化均为**有界并发**（默认 10，见 §5.1.3），并发度过高可能触发 NAS 连接数限制
- 单次整理建议 **< 1000 个文件**（实测 8236 个文件也能跑，仅扫描阶段约 7 s；首次归一化受 Bangumi 3 QPS 限流决定，后续命中缓存后很快）

## 11. 与实施提示词的偏差点（明确说明）

| 项 | 提示词建议 | 实际实现 | 原因 |
| --- | --- | --- | --- |
| 服务端依赖 | TypeScript + 可选 Fastify | TypeScript + **零运行时依赖**（`node:http`） | 减少安装失败面，`npm install` 只装 `typescript` 与 `@types/node` |
| UI 组件库 | Ant Design + Tailwind（**或**纯 Tailwind 复刻 Demo） | **直接复用 Demo 的 CSS 设计令牌**，不引入 UI 库 | 保证与 `demo/index.html` 像素级一致的视觉验收（A14） |
| 图表库 | Recharts / ECharts | 与 Demo 同款 **CSS 柱状图** | 保持视觉一致；仅需「各年份数量 / 占用空间」两类柱状图，零依赖即可满足 A20 |
| Tailwind | 建议使用 | 未使用 | 复用 Demo 原生 CSS 更贴近基准，且免去 PostCSS 构建链 |
| 数据源 | 仅 L1 本地别名表 + L2 Bangumi | 增加 **L2b 前置网页检索**（Wikipedia / Kitsu / AniList / Jikan / 可选 Google）与 **文件修改时间** 两条佐证 | 罗马音 ↔ 中文译名算不出相似度，仅靠 Bangumi 会大量停在「待确认」；两条佐证都不改变"以 Bangumi 官方中文名 + 首播年月为准"的结论 |
| Google 检索 | 用户要求"先过谷歌" | Google Programmable Search（**可选**，需自备 Key + cx）；不填则用免费的 Wikipedia / Kitsu 等价替代 | Google Custom Search 需 API Key 且无免费匿名接口；爬取 google.com 违反其服务条款，故走官方 API 并提供免费替代方案 |

> 除上表外，其余需求（含决策记录 13.1–13.4 的全部条目）均按 `docs/需求与设计文档.md` v0.5 实现。
